# 测试策略（testing.md）

[English](testing.md) | 中文

本仓库如何判定什么叫「已验证」。[dev/README.md](../dev/README.zh.md) 第 06 站 owns 生命周期的入口与出口；本文件 owns 策略。下面的规则对任何仓库都成立；命令是本套件自己的，所以每一条都确实跑得起来。

## 层级

每一层级都回答别的层级回答不了的问题。下面的命令是**本套件自己的** —— 它们跑在本套件上，而本套件就是这套策略最小的可运行样例。把套件拷进你的项目时，把它们换成你项目的命令。

| 层 | 命令 | 它证明什么 | 它证明不了什么 |
|---|---|---|---|
| 单元 | `python3 -m unittest discover -s tests -v` | 本套件自己的契约：策略小节、配置结构、证据（evidence）分类；每个主题一个模块，共享夹具在 [tests/harness.py](../tests/harness.py) | 你项目的行为 |
| 记录检查（check） | `python3 tools/check-invariants.py` | 每条已声明的约定在真实代码树上都成立 | 那条约定本身是不是对的 |
| 守卫自检 | `python3 tools/check-invariants.py --self-test` | 每一种检查 kind 都拒绝无效的 fixture，并接受有效的 fixture | 你的 `checks` 条目是否有意义 |
| 证据选择 | `python3 tools/change-scope.py --base <verified-base-ref>` | 哪些改动面（surface）变了、它们需要什么证据 | 那些证据是否充分 |
| 证据执行 + 记录 | `python3 tools/run-evidence.py --base <verified-base-ref>` | 可运行的证据真的跑了，而且每条命令的判定都被写下来 —— `PASS`、`FAIL`，跑不了的记为 `UNKNOWN` | 手工条目，任何工具都判不了 |

这两个脚本都不去抓取 base ref，也不去猜：传一个你刚验证过的 ref。这张表有两条规则：没有命令的层级不算层级；已经被别的层级回答了的层级，删掉它，而不是继续维护。

## 每个改动的证据

不存在通用的本地基线。先给这次改动命名，再挑出**这次改动**可能弄坏的最小证据。

| 改了什么 | 证据 |
|---|---|
| 单个模块里的行为 | 拥有该模块的那条测试，按名字过滤 |
| 会被多个调用方读到的契约 | 拥有它的那条测试，加上每个调用方的测试 |
| 用户或模型可见的输出 | 拥有该输出的 golden 或 replay 用例 |
| 文档或决策（decision）记录（record） | 记录检查（`check-invariants`） |
| 一个守卫、一条检查，或本文件 | `--self-test`，外加一次你亲眼看着它失败的真实违规 |
| 打包、入口、构建配置 | 在仓库之外做一次干净安装，然后把它跑起来 |
| 一个测试、fixture 或 CI 车道 | 跑那条测试；然后证明它能失败 |

**边跑边报；一个交付只留一份档。** `tools/run-evidence.py` 读同一份改动面映射，执行每一条以已知 runner 开头的证据条目，拒绝执行占位符，并打印每条命令的退出码。它执行不了的条目会按**手工**打印 —— 报告绝不把它们说成通过。跑完不落盘；加 `--record` 才把这次交付的唯一一份记录留在 `dev/evidence/` 下，名字写的是它覆盖的改动面与它据以验证的 merge base；同一交付同一判定再跑一次，同样不写。证据到评审人手里走回复；记录是那份回复所声称内容的耐久副本。

**迭代跑窄的，边界跑全的。** `python3 tools/check-invariants.py --changed <verified-base-ref>` 只跑 patterns 命中这次改动的那些检查，并打印它占了整套的几成。整套属于交付边界 —— 每改一次都跑整套，正是本文件禁止的那种重复。

```sh
python3 tools/change-scope.py --base <verified-base-ref>            # what needs evidence
python3 tools/run-evidence.py --base <verified-base-ref>            # run it, report it
python3 tools/run-evidence.py --base <verified-base-ref> --record   # leave the delivery's one record
python3 tools/run-evidence.py --check                               # only verify the declared commands resolve
```

报告确切的命令与观察到的结果。输入没变的检查不要重跑；也不要把重试、跳过或还在等待的 CI 说成通过。

## 测试替身

**只在昂贵或不确定的边界上替换** —— 模型、网络服务、时钟、随机性 —— 下游一律保持真实。手搓的替身只能证明某个接缝在搬字节，不能证明出货路径的行为如断言所述。

- **点名你替换掉的边界。** 用替身顶掉数据库却断言查询计划，或用替身顶掉队列却断言投递顺序，等于在拿自己的替身做断言。
- **保留代码本来就在调用的接口。** 回放录下的一次交换、回环端口上的假服务、同一接口的内存实现 —— 这些都不改动被测代码；而测试伸手进去操作的 stub 会改。
- **替身跑绿不等于覆盖了那条边界。** 有替身时的绿只证明调用点；真正证明这次集成的是那条跑真实边界的层。

## 确定性

在一台安静的工作站上通过、进了 CI 却失败的测试，量的是环境，不是代码。除非配置能证明不是，否则就假定这些层次彼此重叠：同一文件里的测试；不同文件或 worker 进程；同一个 job 里互相独立的闸门进程；共享同一台宿主机的不同 CI job。

- **原子地分配资源。** 用 `listen(0)` 绑定回环端口，并读取服务器报告的端口；绝不先扫描空闲端口、之后再绑定。每个测试用一个私有的临时根目录（`mkdtemp`）。给共享的数据库、套接字和输出路径一个每测试唯一的命名空间。
- **按状态同步，绝不按时间同步。** 等一个就绪事件、一次握手、一个自己拥有的 promise，或一个可观察的条件。sleep 不能证明 setup 已经结束、teardown 已经落定。当测试的对象就是时间时，注入或伪造时钟，并恢复真实定时器。
- **圈住进程级全局状态。** `env`、`cwd`、假定时器、locale 与时区、模块 mock、注册表、全局钩子，都是独占的可变资源。记下原值当时是缺失还是存在，就原样恢复；恢复动作立即登记，并为本地 `finally` 之前的失败留一个 `afterEach` 兜底。
- **释放到静默（quiescence）。** 获取资源后立刻登记清理，这样断言失败也仍会释放资源。调用了 `close()`、`abort()` 或 `kill()` 却不等待自己拥有的完成信号，就是没做完的 teardown。
- **尊重平台语义。** 操作系统拥有的值未必能往返一致。优先选一个到处都成立的观察；某个用例确实做不到时，就在那个平台上排除它并写明理由，而不是为所有人削弱断言。
- **按车道的预算来定超时。** 单个用例的超时会覆盖 runner 的默认值，而不是让位给它，所以写一个更小的字面量，就是在压低 CI 给的额度。要提 hook 预算，就与测试预算一起提。

- **只解析一个面，绝不两个。** 有的模块来自源码、有的来自构建产物的一次运行，两个面都没测准；而陈旧的产物会把同一份状态加载成第二份。先说清这个测试需要哪个面；当被测对象是发布产物时，就启动真实入口，而不是源码路径。

## 阻塞车道与观测车道

不是每条检查都配得上一票否决。每条车道都要声明为 **blocking**（红色结果拦住这次改动）还是 **observational**（红色结果必须被报告并判定，但不拦住它），而且要在声明这条车道的同一个地方声明。

- **把平台特有的失败降级为 observational。绝不删掉它，也绝不削弱它的断言。** 删掉，就在所有地方都丢了信号；削弱，就在原本通过的那些平台上丢了信号。
- **observational 的失败照样要报告。** 它带着命令与输出进证据记录和 review。被默默忽略的观察，就是多绕了几步的删除检查。
- **给每条 observational 车道一条转正路径。** 在指名次数的连续绿灯运行、且没有无法解释的不稳定之后，把它转成 blocking。没有回去的路，observational 车道就会烂成一份没人看的清单。
- **必需检查的判定是唯一一个绝不能坏掉的 job。** 汇总各 blocking 车道的那个东西跑在能拿到的最普通的 runner 上，不装任何东西，不自己派活，只读结果。只有它决定一次改动能不能落地，所以它自己的可用性高于它所报告的任何东西。

车道不是层级：[Tiers](#层级) 表说的是每条命令证明什么，本小节说的是哪些结果被允许拦住一次改动。

## 证明新守卫

只有在回归能让它失败时，守卫才算是守卫。**没有负控制，任何新断言、新检查、新 fixture 都不被接受。**

- 引入这个回归（或被拒绝的用例），看着预期的那条检查失败，然后还原并看着它通过。
- 对竞态，用一道屏障证明这些操作真的重叠；反复跑这条测试不叫竞态测试。
- 对语料、schema 或注册类守卫，临时移除被登记的对象，确认闸门按你说的方向变红。
- 从外部核对状态 —— 文件、事件、日志、退出码、释放 —— 而不是相信组件自己的报告。
- 当守卫是一条已声明的检查时，把负控制加进 `--self-test`，让这份证明能挺过今后的改动。

没人亲眼看着它失败过的守卫，就是打着绿灯的猜测。

## flake 政策

不稳定的测试是测试或产品里的缺陷，绝不是噪声。下面这些都不是根因修复，review 会拒绝：

只在**单独运行**时才通过的测试，是测试本身的缺陷，而不是机器不稳：它持有另一个测试也在用的状态，或者依赖了 runner 恰好采用的顺序。去修所有权或顺序 —— 把它串行化正是下面被否掉的修法之一。

1. 不点名所等待的状态，就把超时调大；
2. 加重试；
3. 把所有文件改成串行；
4. 吞掉一个错误或一个未处理的 rejection；
5. 削弱断言；
6. 把不稳定的行为归一化掉；
7. 在清理之前或断言之前加 sleep。

两个例外，都很窄，而且都要在这次改动里点名：

- **外部的不确定性。** 对象是真实外部提供方的测试可以重试。把重试留在这个边界上，别处一律不许，并说明是哪个边界。
- **把已给的预算还回去。** 把一个测试套提到它本来就有的车道预算，或按实际测到的争用来给一次有界重试定规模，都是在点名所等待的工作、把车道给过的额度还回去。两者都不是围着一段没人查过的等待凭空造余量。

把测试套串行化也不等于隔离：一个顺序块保护不了宿主机资源不被另一个文件、进程或 job 碰到。应当收窄独占范围，或者干脆修好资源分配。

共享夹具住在自己的模块里，绝不放进另一个测试文件：收集或导入一个测试文件会让它的用例再跑一遍，于是夹具的 setup 与它的真实副作用都会发生两次。

## 已知边界

`testing-policy` 只保证本文件那七节**存在且不为空**。这些分层是不是选对了、证据映射是否真能抓住回归、flake 策略有没有被遵守，全都在闸门之外 —— 那一半属于 [engineer-tests](../.agents/skills/engineer-tests/SKILL.md) 与评审。"这条命令证明这一层"这类主张同理：套件不会替你去跑它。
