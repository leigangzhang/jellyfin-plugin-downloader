# Decision: 意图 —— 「下载失败」这个目标被切成哪几个决定、按什么顺序

[English](2026-10-15-intent-download-fix-decisions.md) | 中文

Status: implemented
Date: 2026-10-15
Class: process

## 问题

这台机器的主人想要一个还没有进媒体库的片子：把片名交出去，拿到内容。实际发生的是，系统
要么毫无反应，要么把它已经取到的部分丢掉——于是既没有内容，也没有一条他能据以行动的报错。

代价在改动之前就是可观测的：

- 八次提交每次都在 **105–228 ms** 内被拒——每一次都是，而这台机器上同一条代码路径本应花满
  25 秒的元数据窗口。
- 用出厂默认，同一个片名返回 **0 条候选**；把其中一个字段关掉返回 43 条，另两个片名分别是
  0 → 19、0 → 6。
- 被拒任务的数据**在磁盘上任何地方都不存在**（按发布名、按半成品后缀、按当天新写入的大文件
  三种搜法全部为空），而任务记录自称已取 13.02 GB、已校验 0 字节。

所以这个目标里装着好几个决定，而不是一个。本记录说明它们是哪些、各属哪一类、以及它们之间
的顺序为什么是这样——好让下一个读者能分清「提案」与「修 bug」，而不是把一切都塞进同一档
流程重量里。

## 决策

六个决定，其中三个需要提案、三个是无需提案的 bug 修复。

**D1 —— 谁负责把外部工具就位，运行期又怎么找到它们。** 类别：`feature`。
现在：`install.sh` 解析 `aria2c`/`ffprobe`/`ffmpeg`，已有的跳过、缺的装上，并把绝对路径记录到
`<插件目录>/backend-tools.json`；`ToolLocator.cs` 按 *配置项 → 记录文件 → `PATH` → 常见前缀*
四级解析；`BackendManager` 把工具目录前置进子进程 `PATH` 并注入 `JMD_ARIA2C_PATH`/
`JMD_FFPROBE_PATH`/`JMD_FFMPEG_PATH`；后端统一走 `tool_path()`，找不到时抛 `ToolMissing`
（`RuntimeError` 的子类，刻意不是 `OSError`），不再让旧的
`except (OSError, …): return []` 把「工具缺失」翻译成「这个种子里没有可读视频」。
这一个决定内部的交付分期是：检测/安装/记录 → 定位器与注入 → 不再吞错 → 一条钉住它的守卫。

**D2 —— 一次搜索的默认可达性是什么。** 类别：`feature`。
现在：`publisher_only_default(kind)` 对 `episode` 为 `True`，对 `movie`、`record`、`variety` 为
`False`；`keywords_for(kind)` 给剧集保留三条剧集署名关键字，给电影与纪录片用
`高清影视之家`/`HDBTHD`；解析后的 `kind` 会传到搜索子进程（`backend/console_server.py` 追加
`--kind`）；面板在目标库是 Records 时发 `record`。

**D3 —— 提交要不要一条逃生通道。** 类别：`feature`。
现在：`/api/submit` 接受 `trust_magnet`（默认 false，不带该字段时命令行与修复前逐字一致），
面板把它做成默认关闭的开关。

**D4 —— 一个任务被拒时数据怎么办。** 类别：`bug-fix`；按意图这一步的判据表（"只让既有行为
符合已声明"）它不需要提案。
现在：`reject_and_preserve` 只记录、只返回，既不碰任务行也不碰文件；`--replace-existing` 回答
`REPLACE_BLOCKED` 并以退出码 7 结束；`--quarantine-rejected` 是可选的另一条路，它把文件**移动**
到 `<staging>/.rejected/<info_hash>/` 并写一份 `REJECTED.json`，而不是删除；
`watch_download.py` 的慢任务中止只打
`ABORT_SLOW_TASK … (task left running; no client DB write, no file removal)`。

**D5 —— 评分阈值控件怎么办。** 类别：`simplification`。
现在：面板只显示一行只读的 `≥N 分`，其唯一来源是配置里的 `MinScore`（60）；五档选择器被移除，
因为这个控件没有能用它的消费者——它的「降低阈值」按钮写的是 55，而 55 从来不在它的选项里。

**D6 —— 无需提案的那些缺陷。** 类别：`bug-fix`。
现在已修：`/api/submit` 与 `/api/watch` 经由同一份共享的 `resolve_year` 解析年份（载荷不再带
`""`）；季页面不再把一季标成「电影」；手动面板会跟着它选定的类型切到目标库，并会从磁盘读回
快照；`write_task_magent` 按 `info_hash` 而不是按目录判断；`tools/check-invariants.py` 的汇总行
把每一类失败都算进去。

**顺序。** D1 先行，因为它是*任何*提交能成立的前提；D2 与 D3 彼此独立、并行做；D4 与 D6 这组
是随发现随并入的。

## 曾考虑的替代方案

**把 Homebrew 目录追加进 `PATH`。** 这是最初的 P0 建议，它输了：那等于把一台机器的前缀写死进
修复里，换 MacPorts 或 `/usr/local` 装的机器会以同样的方式失败、只是目录不同。安装期就位 +
记录解析结果保留了同一个失败模式（工具缺失），却让*修复*与前缀无关，也让配置页能报出缺的是
哪个工具、该跑什么命令。

**在面板上加一个「单源」开关，保留全局默认。** 它输给了按条目类型给默认：开关等于要求使用者
去理解一个他看不见含义的字段，而按类型给默认让「我要一部电影」无需任何人学习这个字段的名字
就能成立。把它定下来的是实测覆盖率——光靠裸片名这一档就能命中 8 个抽样片名里的 7 个，而单源
默认恰恰是把这一档裁掉的东西。

**给阈值选择器补上缺的 55 档。** 它输给了移除整个控件：这套档位是为了服务一个没人会做的比较，
而只读那一行仍然如实显示闸门正在用的值。

**拒绝时继续删，或者先移到隔离区再删。** 两者都输了。删除正是本次报告的成因——任务留在客户端
里、字节没了，从外面看这场「继续下载」的报错根本解释不通；先移后删是同一个损失多一步。可选的
隔离保住了字节可回收，并把决定交还给唯一能权衡「这个种子死了」与「我仍然要这个文件」的人。

**去找一个受支持的接口，绕开直接写客户端数据库。** 这一条是查过而不是假设的：
`plutil -p /Applications/Thunder.app/Contents/Info.plist` 只声明了
`thunder`、`ed2k`、`magnet`、`birdcmd`、`xunleiapp`、`thunderExtension`——每一个都是「添加任务」
类的 scheme。既然没有受支持的暂停/删除/选片接口，诚实的答案是**什么都不写**并把这个结论说出来，
而不是继续在它背后改它的 SQLite。

## 后果

在「按正常方式启动媒体服务」的机器上，提交现在能成立（在元数据闸门里花掉 26.7 秒，而修复前是
105–228 ms 立即拒绝）；电影与纪录片在出厂默认下就有候选；被拒任务保留它的字节。

现在做不到或不再支持的事：插件不再自行暂停、删除或重选一个任务里的文件，因为客户端没有提供
对应接口；清理是显式的（`cleanup_download.py`，或 `--quarantine-rejected`），被拒任务留在客户端
里由人来决定。

刻意不做、各自带着「什么条件下应当重访」的事：

- 为一个最终没建成任务的候选起的 watcher，会以 `status=running` 且 `taskid=None` 停留最长约
  45 分钟。有人再次观察到「监控了但始终没挂上任务」时重访。
- 两套 ETA 口径并存：提交闸门的 `--eta-max-hours 4`，与 watcher 的 `--abort-eta-hours 6` 加三次
  计数。出现第一例「提交时合格、随后被判太慢」的真实反馈时重访。
- 被拒提交留下的空暂存目录壳没有被回收。
- 手动面板对磁盘快照的利用，仍然无法从面板本身被发现。
- `rc=5 PATCH_NOT_APPLIED` 这条路径有守卫覆盖，但本次**没有**在真机上复现：已有任务快路径与
  已成死种的 swarm 拦下了每一次尝试。换一个元数据能取到、选片补丁随后失败的候选时重访。
- 客户端自己记录里的 `-6009` 与 `errno_code=114006` 仍然没有解释：没有公开文档，本机也没有
  客户端日志。
- `~/.agents/skills/jellyfin-movie-downloader/` 下那份独立副本带着同样的「拒绝即删数据」行为，
  已在同一天对齐（它自己的测试 35 项通过）。它是独立副本而非镜像，所以还会再漂移——任何一侧
  下次改动拒绝路径时重访。
- 综艺是否也要单源：提出剧集规则的人 2026-10-15 确认保持现状——只有剧集单源，电影、纪录片、
  综艺都走完整阶梯。综艺候选变少、或综艺搜索返回空时重访。

- 零种子候选：同上一位使用方在 2026-10-15 收紧了口径——磁力候选 `seeds <= 0`（或完全没有读数）
  在获取资源时就被丢弃，既不落盘也不展示；云盘通道没有「做种」这个概念，原样放行。此前那版保留
  「0 种子 / N 个 peer」的行，是被真机证据推翻的：这样一条候选被接受并建成了任务，随后只有几 KB/s、
  预计一天以上才下得完。
- 提交时的 ETA 上限、以及提交后是否自动挂监控，刻意保持现状（2026-10-15 决定）。重访条件：再出现一条
  被接受、随后实测远慢于探测结果、而当其时没有任何东西在盯它的任务。
- 面板计数沿用的 rejected 原因串仍是 `dead_swarm_filtered`，而它现在记录的规则是「没有做种」。
  重访条件：下次改动 Web 分片时把两者对齐。
