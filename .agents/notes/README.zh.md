# 决策记录

[English](README.md) | 中文

这里住着一类设计文档。**决策记录**留下一个塑造本套件的决定或提案 —— *为什么*、它比下去了什么、代价是什么：代码与文档承载不了的那些部分。本文件规定记录住在哪、何时需要写一份，以及文件内的格式。

## 布局与命名

每份记录有两根轴，都写在它的**路径**里 —— `.agents/notes/{lifecycle}/{class}/yyyy-mm-dd-topic-title.md`：

- **生命周期**（顶层目录）是记录的状态，状态改变时记录在目录之间移动：
  - **`proposed/`** —— 已设计但未实现，或只完成了一部分；闸门 `decision-proposed`。
  - **`implemented/`** —— 决定已交付，并且**与真正交付的东西保持一致**：之后路径、名字或默认值移动时，记录在同一次改动里跟着改 —— 只改事实，绝不改决定；闸门 `decision-implemented`、`no-proposal-era-headings`。
  - **`rejected/`** —— 考虑过并否决；只在它的理由还能阻止一个诱人的、有分量的错误时留着，否则连三件套一起删掉；闸门 `decision-rejected`。
- **类目**（嵌套目录）是决定的*种类*，取自下一节的封闭集合；闸门 `note-class`。

文件名里的日期是这件事**第一次被提出**的日期，以 git 历史为准。记录之间的交叉引用一律用相对 Markdown 链接，绝不用裸文字或编号：链接能挺过搬动，而且 `pair-docs.py --check` 会解析它的 fragment。

活跃的那棵树就是清单：浏览它的生命周期与类目目录，或者从 [docs/README.md](../../docs/README.zh.md) 的索引进来。不要为它再加一个集中索引页：第二份清单就是第二个事实。仍有历史价值、但不太会再指导未来工作的记录，会移进下面说的冻结的 `archived/` 树。

模板住在上一层，即 `.agents/notes/<lifecycle>/TEMPLATE.md` —— 骨架由生命周期决定，不由类目决定 —— 每个模板还负责让对应检查不至于匹配不到文件，因为空语料判无效，而不是判通过。

## 分类

每份记录属于一个写在路径里的类目，封闭集合声明在 [workflow.json](../../tools/workflow.json) 的 `note-class` 检查中。闸门会拒掉集合之外的目录、未知的生命周期、缺失的 `Class:` 行，以及与所在目录不一致的 `Class:` 行。新增一个类目，就是在同一次改动里既改那个列表、又改这张表。

| 类目 | 覆盖什么 |
|---|---|
| `feature` | 面向用户或模型的新能力。 |
| `bug-fix` | 修掉一个缺陷，或补上一条事故记录暴露出来的缺口。 |
| `simplification` | 删掉行为或表面积，而不新增能力。 |
| `architecture` | 关于本套件**交付物本身**的结构性决定 —— 各部分怎么关联、词汇是什么。 |
| `process` | 交付物**周围**的工具、政策或流程：闸门、记录、发布、文档规则。 |
| `testing` | 测试基础设施与策略。 |

**架构 vs 流程**这条界线：架构讲的是交付物本身；流程讲的是它周围的机器、以及治理这台机器的规则。`refactor` 是有意缺席的 —— 它唯一的判别标准"可观测行为变了吗？"已经属于 `simplification`。

## 模块

记录的标题以这件事所属的**主题**开头：决定所关于的那个领域，绝不是它被归入的目录，也不是它描述的代码待的地方。一条记录是某一个主题的子记录，而代码搬动不会让它换主题。闸门 `note-class` 会拒掉首词不在下表里的新标题。

上面的类目集合是闭集、采自主项目。这一份是开集、属于本项目自己：一个主题只命名一次、此后复用；当一条决定属于这里还没有名字的领域时，它才增长；新项目从它的第一个条目开始。

| 模块 | 覆盖什么 |
|---|---|
| `adoption` | 把套件拷进来：什么会跟过去，什么不该。 |
| `docs` | 常设文档 —— 种类、归属、预算、发布。 |
| `gates` | 检查引擎、它跑的检查，以及它们读的证据。 |
| `i18n` | 成对文档：什么成对，两侧怎么保持一致。 |
| `intent` | 目标变成提案 —— 几份、哪一类、由什么判定。 |
| `lifecycle` | 十一站、层级阶梯、三种版本状态。 |
| `ranking` | 找到候选、给它们打分、决定取哪一个：池子、信号、排序。 |
| `records` | 记录本身 —— 规则、布局、分类法、标题、退场。 |
| `testing` | 测试基础设施、分层、flake 政策。 |
| `trust` | agent 对自己产出的信号所持的立场。 |

**这份清单怎么维护。** 命名文件之前先查主题，按读者会搜的词查 —— 相近就算命中。只要这个决定落在某个条目已经命名的领域里，就复用它；清单随每条记录增长，就是没人读的清单。只有当这里没有任何条目是这个决定所在之处时，才新增一行 —— 与需要它的那条记录同一次改动 —— 而且名字是**领域，不是话题**：`sandbox`，不是 `new-sandbox-flag`。绝不重命名一条已被记录使用的条目，因为记录靠路径被寻址：拆开的主题获得第二行，而第一行只在最后一条用过它的记录消失后才离开。倒过来也一样 —— 一个读者无法借它抵达任何文件的条目，是一个迟早会被误用的名字。

## 归档与删除

只描述机械改动或局部调整的已实现记录，连同它的英文、中文与 sidecar 文件一起删掉，并修好每一条入链。一个小的缺陷修复、一个新能力，或一个实质性的决定，不会因为实现小就够格被删。

当决定已经完整、它的理由不太可能再指导未来的工作、而这份记录仍然对某段历史负责时，把它封进 `.agents/notes/archived/{class}/yyyy-mm-dd-topic-title.md`。那条路径里有意没有 `implemented`，因为只有已实现记录能进归档。只要它的被否方案、归属边界、某条负向保证、持久化或协议语义、某条安全规则，或重新引入的条件还在指导人，就让它留在活跃树里。**永远不要封存一份提案**：过时的提案应当被否决。被否决的记录只在它还能阻止一个似是而非的错误时才留着，否则连三件套一起删掉。删除、合并还是封存，按 [migrate-and-retire](../skills/migrate-and-retire/SKILL.md) 里那套校准过的做法判，绝不按词数、年龄或配额；选择器本身住在 [evolution.md](../../docs/evolution.md)。

归档会移动完整的三件套、保留 `Status: implemented`，在两种语言的文件里紧跟状态行插入同一行 `Archived: <yyyy-mm-dd>`，重录 sidecar，并修复或删除入链。这些是归档期间唯一允许的内容改动；既有的标题标点、空行布局与语言切换器措辞不构成归档障碍，随正文一起保留。闸门 `archive-seal` 把每份被封存文件的文本与它的摘要、归档日期、以及 [manifest.json](archived/manifest.json) 里写下的理由绑在一起，所以未登记的掉落、丢失的文件、被改动的字节、与登记不一致的日期都会变红。一旦封存，记录即冻结：永不编辑、重排、翻译、更新、移动或删除，也永不拿它当作当前行为的权威。文档闸门会跳过归档来源，包括它们的外链；而活跃正文在有意引用历史时，仍然可以链进一份归档记录。
## 何时需要写一份

只有当代码、测试和现有文档未能解释的决策理由具有长期价值时，才在落地本次工作的同一次交付中新增或更新记录 —— 有 PR 时是同一个 PR，没有时是落地它的那次提交。对未来重大工作的提案从 `proposed/` 起步；已经做出的决定从 `implemented/` 起步。选择与决定匹配的类目文件夹（[含义](#分类)）。

更新**已经拥有该决定**的那份记录，就算满足了这条规则，所以不要造第二份。机械改动与局部调整豁免，包括局部呈现与交互调整。记录绝不被改写成**另一个**决定：写一份新的并交叉引用，除非旧的那份后来按下方的规则被完全合并。把 `implemented/` 记录改成与交付物一致 —— 跟踪它现有的决定落在哪 —— 是要求，不是禁止。

被完全取代的已实现记录，可以合并进当前拥有该决定的记录并删除。删除前，承接方必须保留每一条独特的理由、备选方案、后果、必需的验证和已点名的覆盖缺口；修复每一条入链；并在同一次改动里删除中文对侧文件与一致性记录。部分取代不符合条件：让两份记录互相交叉引用，并更新所有仍然为真的事实。合并不得把旧记录改写成它的反面，也不得依赖 git 历史作为它理由的唯一副本。

只有当一项能力已从生产代码、配置、schema、持久化或协议格式、迁移与兼容行为中完全消失、当前文档不再把它描述为可用、且没有测试把它当作受支持行为来跑时，新增该能力的记录才可合并进后续的移除记录。移除的理由与验证该能力已不存在的测试可以保留。移除方保留最初动机、为什么它已不足以证明保留该能力的合理性、完全移除之外的备选、放弃的能力、重新引入的条件，以及「已彻底移除」的验证。过时的实现清单和只验证已删除行为的测试不属于当前验证证据。只移除一种传输、默认值、实现或呈现属于部分取代；仍有任何持久数据或兼容处理也同样如此。

记录由人来写，不由产出工作的那一轮来写：`/record-decision` 把一个会话定下来的决定冻结成记录（[技能](../skills/record-decision/SKILL.md)）。

## 文件格式

每份活跃记录都遵循同一种文件内格式，由 `decision-proposed`、`decision-implemented`、`no-proposal-era-headings`、`criteria-traced` 与 `note-class` 执行。字面的骨架就是那些模板 —— 格式只有一份，不是两份。已封存的记录保留封存当时的格式，外加上面那行归档日期。

### 头部块

每份记录开头都是下面这几行，顺序如此：

| 行 | 取值 |
|---|---|
| `# Proposal: <title>` 或 `# Decision: <title>` | 生命周期自己的前缀：提案保持 `Proposal`，移动过的记录带 `Decision` |
| `Status: <status>` | `proposed`、`implemented`，或 `rejected — <一行理由>`；必须与所在目录一致 |
| `Date: <yyyy-mm-dd>` | 第一次被提出的日期，与文件名里的日期相同 |
| `Class: <class>` | 路径里的类目，逐字相同；`note-class` 会拿它与目录交叉核对 |

状态里不写日期，也不写除否决理由以外的任何括号内容 —— 日期由文件名承载，其余一切由记录本身承载。以修订形式通过的记录，把修订写在正文里，不写在状态行上。否决理由是状态行里唯一带内容的那一种，因为被否记录的判决正是读者来取的事实。

### 正文骨架

每份记录都以 `## Problem` 开头 —— 动机，要写成离开方案也能独立成立。反复出现的小节只用下面这些名字，别的都不用；真正专有的小节 —— 某道闸门的契约、某种表格形状、某种包拓扑 —— 夹在必需小节之间。

- `proposed/`：`## Problem` · `## Proposal` · `## Alternatives considered` · `## Acceptance criteria` · `## Risks`。
- `implemented/`：`## Problem` · `## Decision` · `## Alternatives considered` · `## Consequences` · `## Testing`。
- `rejected/`：冻结的提案；判定写在 `Status:` 行上。

`## Proposal` 可以用将来时 —— 工作还没落地时，计划、迁移步骤与开放问题都属于它。`## Acceptance criteria` 说清楚什么可观测状态算完成。`## Risks` 同时覆盖可能出什么错、以及这次改动有意放弃了什么。`## Decision` 用现在时陈述已交付的现实。`## Testing` 让每条验收编号活下来，而 `## Consequences` 记下这次取舍付出了什么、又换来了什么。`## Deferred` 或 `## Related` 小节在陈述现在时事实时是允许的。被否记录保留它提案时曾有的一切小节，包括 `## Acceptance criteria` 或 `## Plan`；对它适用的只有头部块、`## Problem` 开头、`## Proposal` 一节，以及强制要求的备选方案一节。

### 曾考虑的替代方案——必需

每份记录都带 `## Alternatives considered`，且不得为空：每个真正的替代方案都要写明它为什么输了，一个加粗起头的段落一条，有争议的可以写成 `### Why not <X>?` 小节。没写下被它比下去什么的决定，会招来重新争论。替代方案是记录下来的，不是编出来的。这条要求在两种语言下都有闸门，所以翻译过的记录不可能悄悄把它丢掉。

### 在生命周期之间移动

移动记录，就是在同一次改动里更新 `Status:` 行、并重新满足目标目录的骨架 —— 否则闸门会让这次移动失败。`proposed/` → `implemented/` 把 `## Proposal` 改写成现在时的 `## Decision`，把 `## Acceptance criteria` 与 `## Risks` 折叠进 `## Consequences`（或者对「如今钉住行为」的那部分写成现在时的 `## Testing`），并保留每一条验收编号 —— 编号正是告诉读者哪条检查证明哪条标准的东西。`proposed/` → `rejected/` 只把理由加到状态行上并冻结正文。闸门 `no-proposal-era-headings` 会拒掉仍带着 `## Proposal`、`## Plan`、`## Migration plan` 或 `## Acceptance criteria` 的已移动记录。

### 中文对侧文件

`.zh.md` 对侧逐节镜像它的英文同侧的结构，并在这对文件旁放一份 `.i18n.yaml` 一致性记录（[i18n.md](../../docs/i18n.md)）。机器检查的头部记号 —— `# Proposal: `、`# Decision: `，以及 `Status:`、`Date:`、`Class:` 三行 —— 逐字保持英文；只有标题与正文被翻译。格式闸门跳过 `.zh.md` 文件；配对闸门检查它们的连续性。

## 去哪看

- 怎么写：骨架在 [.agents/notes/proposed/TEMPLATE.md](proposed/TEMPLATE.md) 与 [.agents/notes/implemented/TEMPLATE.md](implemented/TEMPLATE.md)。
- 一个目标怎么变成一到多份记录：[.agents/skills/shape-intent/SKILL.md](../skills/shape-intent/SKILL.md) 里的触发器。
- 一次改动该写哪份记录：[evolution.md](../../docs/evolution.md) 里的选择器。
- 每一节必须写什么：[documentation.md](../../docs/documentation.md) 里的文档 kind。
- 上面那些规则，以及 `proposed/` 与 `implemented/` 里的骨架：本套件自己不带任何记录；某个项目的记录会在这里累积，按文件名从新到旧。
